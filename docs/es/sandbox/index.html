OpenShift Dev Spaces

Developer Sandbox

Abrí el repo en un workspace y llamá al Granite que el sandbox ya sirve. Este recorrido no instala el gateway de OpenShell y no pide una GPU. El mecanismo es el de camel-k-devsandbox.

Abrir en Developer Sandbox

1Abrir el workspace

Usá el botón, o en el Developer Sandbox abrí Dev Spaces y creá un workspace con este repo. devfile.yaml pide 512Mi / 200m y limita el contenedor a 4Gi / 2 CPUs. El storage es efímero. Ninguna tarea corre al arrancar. Los comandos están en Defining commands.

2Project status

Terminal → Run Task… → Project status. Corre scripts/sandbox-status.sh y muestra oc whoami, el proyecto y la cuota. Las cuotas también cuentan el pod del workspace. El nombre de la tarea queda en inglés porque es el texto del IDE.

3Ask Granite

La tarea Ask Granite corre scripts/sandbox-ask.sh curl. El token es oc whoami -t y no se escribe en git. TLS usa la CA de servicio. La URL base por defecto es:

https://isvc-granite-31-8b-fp8-predictor.sandbox-shared-models.svc.cluster.local:8443/v1

El script lista /v1/models y manda un chat completion. La guía de Red Hat es consumir los modelos con GPU del sandbox. Esta tarea no se ejecutó en la máquina donde se probó el camino local.

4Ask with ask.py

La tarea Ask with ask.py hace el mismo descubrimiento y después corre python3 examples/ask.py con OPENAI_BASE_URL, MODEL_NAME, RHOAI_API_TOKEN y SSL_CERT_FILE. El prompt del script es una frase en español.

5Clean

La tarea Clean borra objetos con la etiqueta app.kubernetes.io/part-of=hello-openshell. No borra el modelo compartido ni el workspace.

Camino de administrador. Agent Sandbox, el chart de OpenShell y un Granite 3.3 2B propio piden un clúster que administres. Ese módulo es OpenShift AI.
