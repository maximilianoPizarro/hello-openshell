OpenShift Dev Spaces · Virtualization

Developer Sandbox

Abrí el repo en un workspace. Al arrancar se instala el CLI de OpenShell 0.1.8. El proyecto del sandbox no puede alojar el gateway, así que OpenShift Virtualization corre un guest en ese proyecto: Fedora con minikube, o RHEL con MicroShift. Desde la terminal del workspace, el CLI crea el sandbox en ese gateway. El agente de las tareas 6 y 7 corre dentro del sandbox y llega a Ollama CPU por host.openshell.internal:11434.

Abrir en Developer Sandbox

Fedora + minikube

Tareas 3–7 y 10. Guest por defecto para el sandbox de OpenShell.

RHEL + MicroShift

Start RHEL terminal y después Connect MicroShift. Las mismas tareas Ask cuando el gateway es microshift.

Cloud Shell

Solo el gateway. Ese kernel no tiene Landlock, así que el sandbox no corre.

Local

Podman en tu máquina, último en esta lista.

1Abrir el workspace

Usá el botón, o en el Developer Sandbox abrí Dev Spaces y creá un workspace con este repo. devfile.yaml pide 512Mi / 200m y limita el contenedor a 4Gi / 2 CPUs. El storage es efímero. Al arrancar corre el comando 1. El resto se elige a mano (Terminal → Run Task…). Corrélas en la shell del workspace: esa shell resuelve minikube-vm.<proyecto>.svc.cluster.local y rhel-vm.<proyecto>.svc.cluster.local. Una laptop no.

Estos son los comandos exec. 3. Start minikube VM ya corre 4. Connect minikube gateway al final. 10. OpenShell UI abre el TUI en el browser de Dev Spaces (o la Route del puerto 7681) cuando hay un gateway. Reiniciá el workspace una vez para que exista el endpoint openshell-ui. 3Arrancar la VM Fedora

scripts/sandbox-vm-up.sh muestra oc whoami y la cuota, y aplica deploy/sandbox-minikube-vm.yaml. OpenShift Virtualization clona el DataSource fedora de openshift-virtualization-os-images. No hay imagen propia. runStrategy es Manual. El cloud-init nombra a fedora y baja scripts/minikube-guest-boot.sh.

PiezaValor
Instanciau1.large, 2 vCPU / 8Gi, disco de 30Gi
minikube1.39.0, driver Podman, containerd, --memory=3072 --cpus=2 --disk-size=10g --force
GatewayAgent Sandbox v1.0.10, chart de OpenShell 0.1.8

El script del guest corre como root. minikube 1.39 pide --force (DRV_AS_ROOT). Se detiene si falta landlock en /sys/kernel/security/lsm. Developer Sandbox apaga las VMs Linux a la hora. Si la VM ya existe, el script deja el disco y el cloud-init; un script de arranque nuevo pide 8. Clean. Connect espera hasta 40 minutos a /var/lib/hello-openshell/ready. El log del guest es /var/log/cloud-init-output.log.

4Crear el sandbox

La tarea 5. Create minikube sandbox conecta el CLI a https://127.0.0.1:8080 por un túnel SSH, selecciona el gateway minikube y crea model-check:

openshell gateway select minikube
openshell sandbox create \
  --name model-check \
  --from registry.access.redhat.com/hi/python:3.12 \
  --policy deploy/hi-python.policy.yaml \
  -- /usr/bin/python3.12 -c 'print("ok")'

OpenShell 0.1.8 necesita Landlock ABI v3 en el kernel del guest. Resultado esperado: ok y fase Completed. La tarea 9. Inspect cluster imprime los logs.

5Preguntar desde el sandbox

Las tareas 6 y 7 son el mismo camino que make ask. Crean hello-ask / hello-agent desde registry.access.redhat.com/hi/python:3.12, importan deploy/ollama.profile.yaml y corren examples/ask.py adentro. El supervisor llama a host.openshell.internal:11434 en el guest Fedora, que hace de proxy a Ollama CPU llama3.2:1b en este proyecto (deploy/sandbox-ollama.yaml, tope 4Gi, cuota de GPU 0).

10OpenShell UI

OpenShell 0.1.8 no tiene consola web. La tarea 10. OpenShell UI corre openshell term dentro de ttyd en el puerto 7681. Dev Spaces publica el endpoint openshell-ui como Route. Abrilo desde PORTS o el host de la Route. Dejá la tarea corriendo.

R1Terminal RHEL

La cuota no banca dos VMs u1.large más Ollama. Si minikube-vm está Running, corré 8. Clean primero (o apagá esa VM).

La tarea Start RHEL terminal aplica deploy/sandbox-rhel-vm.yaml. El guest es rhel-vm, clonado del DataSource rhel9 con preferencia rhel.9. El usuario es cloud-user. La contraseña queda en ~/.config/hello-openshell/rhel.password. La clave SSH del workspace es la misma que la de la VM Fedora.

bash scripts/sandbox-rhel-up.sh
ssh -i ~/.config/hello-openshell/minikube_ed25519 -o IdentitiesOnly=yes \
  cloud-user@rhel-vm.$(oc project -q).svc.cluster.local

Desde una laptop, oc port-forward svc/rhel-vm 2222:22 y SSH a 127.0.0.1 en el puerto 2222. Developer Sandbox igual apaga el guest a la hora.

R2Connect MicroShift

Este guest no instala minikube. La imagen del catálogo no tiene suscripción, así que scripts/microshift-guest-boot.sh toma MicroShift 4.22 de mirror.openshift.com y los paquetes base de AlmaLinux 9 (rpm --replacefiles por un conflicto de GPG). Guardá un pull secret de Red Hat en ~/.config/hello-openshell/openshift-pull-secret antes de esta tarea. MicroShift baja quay.io/openshift-release-dev; un secret vacío se rechaza.

bash scripts/sandbox-rhel-connect.sh
openshell gateway add https://127.0.0.1:8080 --local --name microshift
openshell gateway select microshift

El disco no tiene volume group LVM ni provisioner. El volumen del gateway es hostPath. El hostname rhel-vm se fija en /etc/hosts del guest (el script de arranque lo hace) para que el API server no llame al Service al resolver el nodo. El claim del workspace del sandbox es 2Gi en hostPath.

R3Sandbox y Ask en MicroShift

Después de Connect, las mismas tareas 5–7 y 10 apuntan al gateway microshift. Las tareas 6/7 eligen minikube si esa VM está Running; con solo rhel-vm usan MicroShift. Prueba de humo esperada: ok y fase Completed.

openshell gateway select microshift
openshell sandbox create \
  --name model-check \
  --from registry.access.redhat.com/hi/python:3.12 \
  --policy deploy/hi-python.policy.yaml \
  -- /usr/bin/python3.12 -c 'print("ok")'

8Clean

La tarea 8. Clean corta el túnel SSH y borra minikube-vm, rhel-vm, Ollama y los objetos con la etiqueta app.kubernetes.io/part-of=hello-openshell. No borra modelos compartidos ni el workspace.

Gateway. Un proyecto de Developer Sandbox no puede crear CRDs, namespaces ni ClusterRoles, y agents.x-k8s.io no está servida, así que el chart 0.1.8 no se instala en el proyecto. El chart corre dentro del guest (minikube o MicroShift). No pases valores de SCC de OpenShift a minikube. El módulo para un clúster que administres es OpenShift AI. Cloud Shell no puede correr un sandbox: ese kernel no tiene Landlock.
