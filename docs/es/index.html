OpenShift Dev Spaces · Virtualization

Developer Sandbox

OpenShell corre agentes dentro de sandboxes con política explícita de red y de sistema de archivos. En esta guía levantás un gateway en una VM de OpenShift Virtualization, creás un sandbox sin red propia y ejecutás un agente que habla con Ollama en CPU a través de un único host permitido en un perfil.

Necesitás una cuenta gratis de Developer Sandbox y un navegador. El camino B también pide un pull secret de Red Hat. Si es la primera vez, empezá por el camino A (Fedora + minikube).

Guía independiente, sin afiliación ni respaldo de NVIDIA, Red Hat ni Python Software Foundation.

Abrir en Developer Sandbox

Una hora. Developer Sandbox apaga las VM Linux a la hora. Si el estado es Stopped, ejecutá de nuevo A2 o B2. No uses Clean para eso.

Una VM. La cuota admite un guest u1.large más Ollama. Ejecutá A1. Clean o B1. Clean antes de arrancar un camino o de cambiar de guest.

Esperas largas. Dejá correr A2, A3, B2 y B3. No cierres la terminal. El primer arranque de B3 puede tardar decenas de minutos.

Sin GPU. La cuota de GPU es 0, así que Ollama corre en CPU con llama3.2:1b. Las respuestas son lentas y pueden ser cortas o imprecisas.

A2 Arrancá la VM Fedora y Ollama

La tarea A2. Start minikube VM and Ollama imprime oc whoami y la cuota, arranca Ollama en CPU (llama3.2:1b, 4Gi) en este proyecto y aplica deploy/sandbox-minikube-vm.yaml. No hay imagen custom. runStrategy es Manual. El cloud-init en línea nombra fedora y hace curl de scripts/minikube-guest-boot.sh.

Circuito: perfil, provider y agente

A5 / A6 / A9 y B5 / B6 / B9 siguen el mismo camino que make ask. Después de conectar el gateway agregan el perfil de Ollama, registran el provider, crean el sandbox del agente y corren el cliente Python adentro. Podés correr los mismos comandos en la terminal del workspace.

1. Importá el perfil y creá el provider

deploy/ollama.profile.yaml permite solo host.openshell.internal:11434 (REST, enforce). Lista binarios de Python 3 y no guarda ninguna clave. No pongas 127.0.0.1 ni localhost en un perfil: OpenShell siempre bloquea loopback desde el sandbox.

openshell profile lint -f deploy/ollama.profile.yaml
openshell profile import -f deploy/ollama.profile.yaml
openshell provider create --name ollama --type ollama
openshell provider get ollama

Las tareas Ask saltean el import si el perfil ya está en el gateway o en el CLI. already exists es éxito. No corren openshell gateway remove si el gateway ya está conectado.

2. Creá el sandbox del agente

El agente no es un CR aparte. Es un sandbox de OpenShell desde registry.access.redhat.com/hi/python:3.12 con --provider ollama y --policy deploy/hi-python.policy.yaml. A5 lo nombra hello-ask. A6 lo nombra hello-agent. A9 lo nombra hello-turns y corre examples/ask_turns.py. El proceso va inlined como python3.12 -c.

openshell sandbox create \
  --name hello-agent \
  --from registry.access.redhat.com/hi/python:3.12 \
  --provider ollama \
  --policy deploy/hi-python.policy.yaml \
  --env OPENAI_BASE_URL=http://host.openshell.internal:11434/v1 \
  --env MODEL_NAME=llama3.2:1b \
  --env OPENAI_API_KEY=fake \
  --env ASK_PROMPT='Explica en una frase que es un sandbox y por que un agente deberia correr dentro de uno.' \
  -- /usr/bin/python3.12 -c "$(cat examples/ask.py)"

El usuario de la imagen es UID 65532 y su grupo primario es 0, así que la política fija ambos a 65532. fake es un placeholder: el cliente OpenAI pide una clave, Ollama no la valida, y el proceso puede ver el valor. Una credencial real va en un provider, pegada con --provider, no en --env.

3. Cómo sale el pedido del sandbox

  1. ask.py lee OPENAI_BASE_URL y hace POST a /v1/chat/completions (A5 también hace GET a /v1/models).
  2. El perfil permite ese host y puerto. La política permite /usr/bin/python3.12.
  3. El supervisor en el guest marca host.openshell.internal:11434. Connect setea server.hostGatewayIP de OpenShell para que los pods sandbox de Kubernetes resuelvan ese nombre (no tienen DNS propio).
  4. A2 o B2 aplica deploy/sandbox-ollama.yaml (Ollama en CPU llama3.2:1b, 4Gi, cuota GPU 0) y corre un generate en el pod para que el modelo ya esté en memoria. Un /chat/completions en frío por el supervisor se cierra antes del primer token. Connect instala un proxy TCP en el guest para que :11434 reenvíe al ClusterIP de Ollama en este proyecto. El modelo 1b no pelea por los 8Gi del guest.
  5. Ollama responde. El sandbox nunca tiene una ruta propia.

Glosario

Significados como los usa este workshop con OpenShell 0.1.8. Contrastalos con la documentación de OpenShell cuando salga un CLI nuevo.

Gateway
El plano de control de OpenShell que crea sandboxes. Acá corre dentro del cluster del guest (minikube o MicroShift), no en el proyecto de Developer Sandbox.
Sandbox
El proceso aislado donde corre el agente. No tiene red propia y sigue la política y el perfil.
Supervisor
En el guest. Hace la conexión de salida permitida. Acá pega a un proxy TCP en el guest que reenvía a Ollama en este proyecto de OpenShift.
Política
deploy/hi-python.policy.yaml — sistema de archivos y UID. La imagen hardened corre como 65532/65532.
Perfil
deploy/ollama.profile.yaml — el único host que el sandbox puede pedirle al supervisor: host.openshell.internal:11434. Sin credencial. Loopback siempre está bloqueado.
Provider
openshell provider create --name ollama --type ollama — registra Ollama como backend de inferencia con nombre en este gateway.
Agente
Un sandbox de OpenShell (hello-ask, hello-agent o hello-turns) que corre examples/ask.py o examples/ask_turns.py.
Landlock
Restricción del kernel Linux que OpenShell 0.1.8 necesita (ABI v3). Cloud Shell no la expone; la VM guest sí.
hostGatewayIP
La dirección que Connect inyecta para que los pods sandbox resuelvan host.openshell.internal. Los sandboxes de Kubernetes no tienen DNS propio.
DataSource
Objeto de OpenShift Virtualization que nombra la imagen de disco clonable (fedora o rhel9).
MicroShift
Una distribución chica de OpenShift. El camino B corre MicroShift 4.22 dentro de rhel-vm.

Gateway. Un proyecto de Developer Sandbox no puede crear CRDs, namespaces ni ClusterRoles, y agents.x-k8s.io no se sirve, así que el chart Helm 0.1.8 no se puede instalar en el proyecto mismo. El chart corre dentro del guest (minikube o MicroShift). No pases valores de SCC de OpenShift a minikube. Un cluster que administrás es el módulo de OpenShift AI. Cloud Shell no puede correr un sandbox: ese kernel no tiene Landlock.
