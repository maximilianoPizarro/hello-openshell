Developer Sandbox

Abrí el repo en un workspace. Al arrancar se instala el CLI de OpenShell 0.1.8. El proyecto del sandbox no puede alojar el gateway, así que OpenShift Virtualization corre un guest en ese proyecto: Fedora con minikube, o RHEL con MicroShift. Dos recorridos numerados viven en Terminal → Run Task…. La cuota banca una guest u1.large más Ollama, así que corré A1. Clean o B1. Clean antes de un camino. El agente de A5/A6 y B5/B6 corre dentro del sandbox y llega a Ollama CPU por host.openshell.internal:11434.

Abrir en Developer Sandbox

Fedora + minikube

A1 Clean, después A2–A8. Gateway minikube.

RHEL + MicroShift

Pull secret, B2, esperar Running, B3, después B4–B8. Gateway microshift.

Cómo Ask importa ollama.profile.yaml, crea el provider y corre ask.py en el sandbox.

Cloud Shell

Solo el gateway. Ese kernel no tiene Landlock, así que el sandbox no corre.

Local

1Abrir el workspace

Usá el botón, o en el Developer Sandbox abrí Dev Spaces y creá un workspace con este repo. devfile.yaml pide 512Mi / 200m y limita el contenedor a 4Gi / 2 CPUs. El storage es efímero. Al arrancar corre el comando 1. El resto se elige a mano (Terminal → Run Task…). Corrélas en la shell del workspace: esa shell resuelve minikube-vm.<proyecto>.svc.cluster.local y rhel-vm.<proyecto>.svc.cluster.local. Una laptop no.

Piezas del circuito

Policy
deploy/hi-python.policy.yaml — filesystem y UID. La imagen endurecida corre como 65532/65532.
Profile
deploy/ollama.profile.yaml — el único host que el sandbox puede pedirle al supervisor: host.openshell.internal:11434. Sin credencial. Loopback siempre está bloqueado.
Provider
openshell provider create --name ollama --type ollama — registra Ollama como backend de inferencia en este gateway.
Agente
Un sandbox de OpenShell (hello-ask o hello-agent) que corre examples/ask.py. No tiene red propia.
Supervisor
En el guest. Hace la conexión de salida permitida. Acá pega a un proxy TCP del guest que reenvía a Ollama en este proyecto de OpenShift.

A2Arrancar la VM Fedora y Ollama

scripts/sandbox-vm-up.sh muestra oc whoami y la cuota, arranca Ollama CPU (llama3.2:1b, 4Gi) en este proyecto y aplica deploy/sandbox-minikube-vm.yaml. El pull del modelo corre mientras clona el disco del guest, así A5 / A6 no esperan esa imagen. OpenShift Virtualization clona el DataSource fedora de openshift-virtualization-os-images. No hay imagen propia. runStrategy es Manual. El cloud-init nombra a fedora y baja scripts/minikube-guest-boot.sh.

PiezaValor
Instanciau1.large, 2 vCPU / 8Gi, disco de 30Gi
minikube1.39.0, driver Podman, containerd, --memory=3072 --cpus=2 --disk-size=10g --force
GatewayAgent Sandbox v1.0.10, chart de OpenShell 0.1.8

El script del guest corre como root. minikube 1.39 pide --force (DRV_AS_ROOT). Se detiene si falta landlock en /sys/kernel/security/lsm. Developer Sandbox apaga las VMs Linux a la hora. Si la VM ya existe, el script deja el disco y el cloud-init; un script de arranque nuevo pide A1. Clean. Connect espera hasta 40 minutos a /var/lib/hello-openshell/ready. El log del guest es /var/log/cloud-init-output.log. Si SSH dice Offending ED25519 key o Host key verification failed, el guest se recreó y la clave vieja sigue en ~/.config/hello-openshell/known_hosts. Connect olvida esa clave. A1. Clean borra el archivo. Para destrabar la tarea de ahora:

ssh-keygen -R minikube-vm.$(oc project -q).svc.cluster.local \
  -f ~/.config/hello-openshell/known_hosts

A4Crear el sandbox de humo

La tarea A4. Create minikube sandbox conecta el CLI a https://127.0.0.1:8080 por un túnel SSH, selecciona el gateway minikube y crea model-check. Ese sandbox solo imprime ok. Todavía no importa el perfil de Ollama.

openshell gateway select minikube
openshell sandbox create \
  --name model-check \
  --from registry.access.redhat.com/hi/python:3.12 \
  --policy deploy/hi-python.policy.yaml \
  -- /usr/bin/python3.12 -c 'print("ok")'

OpenShell 0.1.8 necesita Landlock ABI v3 en el kernel del guest. Resultado esperado: ok y fase Completed. La tarea A8. Inspect cluster imprime los logs.

A5Perfil, provider y agente

Las tareas A5 / A6 y B5 / B6 son el mismo camino que make ask. Con el gateway conectado, agregan el perfil de Ollama, registran el provider, crean el sandbox del agente y corren examples/ask.py adentro. Podés correr los mismos comandos en la terminal del workspace.

1. Importar el perfil y crear el provider

deploy/ollama.profile.yaml permite solo host.openshell.internal:11434 (REST, enforce). Lista binarios de Python 3 y no guarda clave. No pongas 127.0.0.1 ni localhost en un perfil: OpenShell siempre bloquea loopback desde el sandbox.

openshell profile lint -f deploy/ollama.profile.yaml
openshell profile import -f deploy/ollama.profile.yaml
openshell provider create --name ollama --type ollama
openshell provider get ollama

Ask saltea el import si openshell profile get ollama ya funciona en ese gateway. No corre openshell gateway remove si el gateway ya está conectado, así un segundo Ask no cae en custom provider profile 'ollama' already exists.

2. Crear el sandbox del agente

El agente no es un CR aparte. Es un sandbox de OpenShell desde registry.access.redhat.com/hi/python:3.12 con --provider ollama y --policy deploy/hi-python.policy.yaml. A5 lo nombra hello-ask (lista modelos, prompt en inglés). A6 lo nombra hello-agent (prompt en español). El proceso es examples/ask.py inline como python3.12 -c.

openshell sandbox create \
  --name hello-agent \
  --from registry.access.redhat.com/hi/python:3.12 \
  --provider ollama \
  --policy deploy/hi-python.policy.yaml \
  --env OPENAI_BASE_URL=http://host.openshell.internal:11434/v1 \
  --env MODEL_NAME=llama3.2:1b \
  --env OPENAI_API_KEY=fake \
  --env ASK_PROMPT='Explica en una frase que es un sandbox y por que un agente deberia correr dentro de uno.' \
  -- /usr/bin/python3.12 -c "$(cat examples/ask.py)"

El usuario de la imagen es UID 65532 y su grupo primario es 0, así que la política fija ambos en 65532. fake es un relleno: el cliente OpenAI pide una clave, Ollama no la valida, y el proceso puede ver el valor. Una credencial real va en un provider, con --provider, no en --env.

3. Cómo sale el request del sandbox

  1. ask.py lee OPENAI_BASE_URL y hace POST a /v1/chat/completions (A5 también hace GET a /v1/models).
  2. El perfil permite ese host y puerto. La política permite /usr/bin/python3.12.
  3. El supervisor en el guest llama a host.openshell.internal:11434. Connect fija server.hostGatewayIP de OpenShell para que los pods del sandbox en Kubernetes puedan resolver ese nombre (no tienen DNS propio).
  4. A2 o B2 aplica deploy/sandbox-ollama.yaml (Ollama CPU llama3.2:1b, 4Gi, cuota de GPU 0). Connect instala un proxy TCP en el guest para que :11434 vaya al ClusterIP de Ollama en este proyecto. El modelo 1b no compite por los 8Gi del guest.
  5. Ollama responde. El sandbox nunca tiene ruta propia.

A7OpenShell UI

OpenShell 0.1.8 no tiene consola web. La tarea A7. OpenShell UI (o B7) corre openshell term dentro de ttyd en el puerto 7681. Dev Spaces publica el endpoint openshell-ui como Route. Abrilo desde PORTS o el host de la Route. Dejá la tarea corriendo.

BRHEL + MicroShift, en orden

La cuota no banca dos VMs u1.large más Ollama. Si minikube-vm está Running, corré B1. Clean primero. Después:

  1. Bajá un pull secret de Red Hat en console.redhat.com/openshift/install/pull-secret.
  2. En la terminal de Dev Spaces, guardalo antes de Connect: 
    mkdir -p ~/.config/hello-openshell
# pegá el JSON en ~/.config/hello-openshell/openshift-pull-secret
chmod 600 ~/.config/hello-openshell/openshift-pull-secret
  3. B2. Start RHEL VM and Ollama — crea rhel-vm o la prende si ya existe, y arranca Ollama CPU en este proyecto. Developer Sandbox apaga las VMs Linux a la hora; volvé a correr B2 cuando el status sea Stopped.
  4. Esperá a que la VM esté Running. No arranques B4 todavía.
  5. B3. Connect MicroShift — copia el pull secret, espera a cloud-init (un solo lock de RPM), instala MicroShift si hace falta y registra el gateway microshift. Dejalo correr; el primer boot puede tardar decenas de minutos.
  6. Si B3 dice The guest has no pull secret, falta el archivo del paso 2 o no tiene auths. Arreglá el archivo y volvé a B3. No hace falta Clean.
  7. Si SSH dice Connection refused y vm=Stopped, corré B2 y después B3. No hace falta Clean.
  8. Si SSH dice Offending ED25519 key o Host key verification failed, el guest se recreó. Connect olvida la clave vieja en ~/.config/hello-openshell/known_hosts. No hace falta Clean. Para destrabar ahora: ssh-keygen -R rhel-vm.$(oc project -q).svc.cluster.local -f ~/.config/hello-openshell/known_hosts.
  9. Si ves /var/lib/rpm/.rpm.lock, cloud-init y B3 se pisaron. Esperá y volvé a B3. El script del guest ahora espera ese lock.
  10. Cuando B3 diga que el gateway está up, corré B4, después B5 / B6 (el mismo circuito de perfil, provider y agente), y B7 / B8 si querés el TUI o los logs.

B2VM RHEL y Ollama

La tarea B2. Start RHEL VM and Ollama aplica deploy/sandbox-rhel-vm.yaml y arranca Ollama CPU en este proyecto para que B5 / B6 no esperen el pull del modelo. El guest es rhel-vm, clonado del DataSource rhel9 con preferencia rhel.9. El usuario es cloud-user. La contraseña queda en ~/.config/hello-openshell/rhel.password. La clave SSH del workspace es la misma que la de la VM Fedora. Si el objeto de la VM ya existe, B2 deja el disco y el cloud-init y solo la prende.

bash scripts/sandbox-rhel-up.sh
ssh -i ~/.config/hello-openshell/minikube_ed25519 -o IdentitiesOnly=yes \
  cloud-user@rhel-vm.$(oc project -q).svc.cluster.local

Desde una laptop, oc port-forward svc/rhel-vm 2222:22 y SSH a 127.0.0.1 en el puerto 2222.

B3Connect MicroShift

Este guest no instala minikube. La imagen del catálogo no tiene suscripción, así que scripts/microshift-guest-boot.sh toma MicroShift 4.22 de mirror.openshift.com y los paquetes base de AlmaLinux 9 (rpm --replacefiles por un conflicto de GPG). B3 falla de inmediato si no existe ~/.config/hello-openshell/openshift-pull-secret con un JSON de pull secret de Red Hat que tenga auths. MicroShift baja quay.io/openshift-release-dev; un secret vacío se rechaza. Cloud-init y B3 comparten un lock para no pelearse por /var/lib/rpm/.rpm.lock. Si la VM está Stopped, B3 la arranca de nuevo.

bash scripts/sandbox-rhel-connect.sh
openshell gateway add https://127.0.0.1:8080 --local --name microshift
openshell gateway select microshift

El disco no tiene volume group LVM ni provisioner. El volumen del gateway es hostPath. El hostname rhel-vm se fija en /etc/hosts del guest (el script de arranque lo hace) para que el API server no llame al Service al resolver el nodo. El claim del workspace del sandbox es 2Gi en hostPath.

B4Sandbox y Ask en MicroShift

Después de B3, corré B4 para el sandbox de humo y después B5 / B6 para el mismo circuito de perfil, provider y agente en el gateway microshift. Esas tareas fijan SANDBOX_GATEWAY=microshift para no elegir minikube. Prueba de humo esperada: ok y fase Completed.

openshell gateway select microshift
openshell sandbox create \
  --name model-check \
  --from registry.access.redhat.com/hi/python:3.12 \
  --policy deploy/hi-python.policy.yaml \

A1 / B1Clean

Las tareas A1. Clean y B1. Clean corren el mismo script. Cortan el túnel SSH y borran minikube-vm, rhel-vm, Ollama y los objetos con la etiqueta app.kubernetes.io/part-of=hello-openshell. No borran modelos compartidos ni el workspace. Corré Clean antes de cambiar de guest.

Gateway. Un proyecto de Developer Sandbox no puede crear CRDs, namespaces ni ClusterRoles, y agents.x-k8s.io no está servida, así que el chart 0.1.8 no se instala en el proyecto. El chart corre dentro del guest (minikube o MicroShift). No pases valores de SCC de OpenShift a minikube. El módulo para un clúster que administres es OpenShift AI. Cloud Shell no puede correr un sandbox: ese kernel no tiene Landlock.
